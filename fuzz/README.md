# Fuzzing

libFuzzer targets over every decoder that touches bytes the node did not
produce itself.

## Windows

`cargo fuzz` does not support `x86_64-pc-windows-msvc` — libFuzzer's runtime and
the `-Zsanitizer=address` backend are Linux/macOS only. On a Windows workstation
run these under WSL, or leave them to CI:

```bash
wsl
cd /mnt/d/Maya2C/fuzz
cargo install cargo-fuzz
cargo fuzz run tx_decode
```

## Targets

| Target | Entry point | Property |
|---|---|---|
| `tx_decode` | `Transaction::from_bytes` | no panic; encoding is canonical |
| `header_decode` | `BlockHeader::from_bytes` | accepts exactly the 144-byte strings |
| `block_decode` | `Block::from_bytes` | no panic; no over-reservation; canonical |
| `payload_decode` | `TxKind::decode` | no panic; canonical when the section is the whole input |
| `account_decode` | `Account::decode` | accepts exactly the 16-byte strings |

Every target asserts two things: that a malformed frame surfaces as
`NodeError::Decode` rather than a panic, and that an accepted frame re-encodes
to itself. The second is a real invariant here rather than a nicety —
`ByteReader::finish` rejects trailing bytes and every field is fixed-width or
length-prefixed, so two byte strings decoding to one transaction would mean one
transaction with two txids.

## What the targets deliberately do not call

- **`Transaction::verify` / `HybridVerifyingKey::verify`** — ML-DSA-65 plus
  SLH-DSA-SHA2-128s is ~105 ms per call. A fuzzer capped at ten executions a
  second finds nothing. Signature behaviour is covered by
  `tests/hybrid_tests.rs` and `tests/malleability_tests.rs`.
- **`BlockHeader::pow_hash` / `meets_difficulty`** — ArgonBlake is a 32 MiB
  Argon2id pass, seconds per call.

Signature verification and proof-of-work are not decode concerns. Adding either
to a target would silently disable that target rather than strengthen it.

## Corpus

Seeds are generated by the real encoders, never hand-written. The generator
lives in the node's own crate rather than here, because it has nothing to do
with libFuzzer and this package does not build on Windows:

```bash
# from the repository root, on any platform
cargo run --example gen_fuzz_corpus
```

Hand-rolled seed bytes are a second, undocumented copy of the wire format. When
a field moves they stop decoding, and the fuzzer keeps running against a corpus
that no longer reaches the code it was written for — a failure with no symptom.
`gen_corpus` is deterministic, so regenerating it produces a reviewable diff or
no diff at all.

Seeds sit near the interesting boundaries on purpose: `u64::MAX` output amounts,
a joinsplit whose `public_out + fee` is one mutation from wrapping, a
`SettleBatch` at the `CLOSURE_SIZE` accounting boundary.

## Running

```bash
cargo fuzz run tx_decode -- -max_len=65536 -rss_limit_mb=2048 -timeout=5
```

`-rss_limit_mb` is load-bearing for `block_decode`: a block frame carries a
`u64` transaction count, so a bad bound in `ByteReader::read_collection_len`
shows up as a libFuzzer OOM rather than as a panic.

## When a target crashes

1. Minimize: `cargo fuzz tmin <target> fuzz/artifacts/<target>/<crash>`.
2. Fix the decoder.
3. Add the minimized input as a regression case in the matching
   `tests/*_tests.rs` file — `tests/state_tests.rs` for account records,
   `tests/payload_tests.rs` for payload sections, and so on.
4. Commit the minimized input to `fuzz/corpus/<target>/` as well, so the fuzzer
   keeps the path warm.

Order matters: the regression test lands with the fix, in the same commit.
Committing a reproducer ahead of the fix puts a failing test on the branch.

`fuzz/artifacts/` is git-ignored — crash inputs are uploaded as CI artifacts and
promoted to `corpus/` deliberately, not by accident.
