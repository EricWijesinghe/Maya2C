# 2. Transactions — v0.1.0

Reference: `crates/spec-ref/src/{wire,stf}.rs`. Node: `Transaction::verify`,
`Transaction::sender`, `StateDB::stage_transaction`.

- **TX-1** A transaction authorizes nothing unless **both** its ML-DSA-65 (FIPS 204) and SLH-DSA-SHA2-128s (FIPS 205) signatures verify over TX-3's bytes. This is checked before any balance rule, and after the nonce check (STF-1), which is a cheaper refusal of a stale transaction; both orders accept the same transactions. A block containing a transaction that fails it is invalid.
- **TX-2** The sender is derived, never read from the wire: `blake3("custom-l1-node.address.v3" ‖ ml_dsa_pk ‖ slh_dsa_pk)`. *(positive only: defines a value)*
- **TX-3** Both signatures sign `"custom-l1-node.tx.v4" ‖ chain_tag ‖ io_section ‖ public_key ‖ nonce_u64` (plus the payload encoding for version 6), where `chain_tag` is TX-5's. The keys are inside the signed bytes, so each signature commits to the other scheme's key. Suite-tagged (v7) and multisig (v8) transactions sign under `"custom-l1-node.tx.suite.v2"` and `"custom-l1-node.tx.multisig.v2"`, each followed by `chain_tag` and then their own fields. *(positive only: defines a value)*
- **TX-5** `chain_tag` is the 32-byte id (CON-2) of the genesis block of the one chain a signature is valid on. It is signed, never sent: the wire format (ENC-2) carries no tag, and a node verifies with its own genesis id, so a frame signed for any other chain — another network, or an earlier genesis of the same one — fails TX-1. A node that has not bound its genesis verifies nothing. (ADR-036.)
- **TX-4** Suite-tagged (v7) and multisig (v8) transactions verify only through the height-aware `verify_at`, at or past `SUITE_ENVELOPE_ACTIVATION_HEIGHT` — `0` since ADR-013, so from genesis — under the suite registry's policy; `Transaction::verify`, which has no height, refuses them.

## Sponsored frames (ADR-135 P-4, wire v13, dark until feature bit 44)

Vectors: `spec/tests/sponsored.json`, laid by hand from these layouts rather than generated by `crates/spec-ref`. Node: `core::sponsor_tx`, `state::sponsor`.

- **SP-1** A sponsored frame is `0x0D ‖ inner_len(4 LE) ‖ inner ‖ suite(1) ‖ pk_len(4 LE) ‖ sponsor_pk ‖ max_fee(32 LE) ‖ valid_until(8 LE) ‖ sig_len(4 LE) ‖ signature`. `inner` is one complete frame of any other version. A sponsored frame is never an inner frame at any depth: an inner whose first byte is `0x0D` is refused before it is parsed, no other version on this branch carries an inner frame, and a later wrapping version (such as v10 stealth) must refuse a `0x0D` inner the same way, or a sponsorship could nest past depth 1. `pk_len` and `sig_len` must equal the suite registry's lengths. A truncated frame, an unknown suite, a wrong length or a trailing byte is a decode error.
- **SP-2** The sponsor signs `"maya2c/sponsor/v1" ‖ chain_tag(32) ‖ txid(inner)(32) ‖ max_fee(32 LE) ‖ valid_until(8 LE)`, where `txid(inner)` is the inner frame's own id and `chain_tag` is TX-5's. The outer frame's id hashes the inner id and every sponsor field, so two sponsorships of one inner have two ids. *(positive only: defines a value)*
- **SP-3** A sponsored frame applies only if the inner frame has no output to the fee collector, `height <= valid_until`, and `required(outer_len) <= max_fee`, where `required` is FEE-5's `base_fee × size_bytes` over the whole outer frame.
- **SP-4** On apply the sponsor (`suite_address(suite, sponsor_pk)`) is debited `required(outer_len)` by one checked subtraction, credited to the fee collector and booked for the base-fee burn exactly as an unsponsored fee is; then the inner applies by every rule it would alone, against its own sender. If either step fails the whole frame is refused and no nonce is consumed. A sponsor that is a vault has the debit counted, in full, against its instant window (invariant 32).
- **SP-5** `Transaction::verify` refuses every sponsored frame. `verify_at` verifies the inner frame by TX-1/TX-4, then that the sponsor's suite is admissible at the height and that its signature verifies over SP-2's bytes. Both halves must pass.
- **SP-6** Below the activation height of feature bit 44 every sponsored frame is refused, on mempool admission and on apply, by the same check. The compiled height is `u64::MAX`.

Open residuals, each a blocker for writing `SPONSORED_FEES_ACTIVATION_HEIGHT` (V4-V1 red team, `crates/node/tests/v4_redteam_sponsored.rs`; BACKLOG "v4 activation blockers"):

- M1, approval swap: A multisig inner's approvals are outside `txid(inner)`, so a relay can swap which members signed a mixed-suite quorum (ML-DSA-87 for ML-DSA-65): the frame grows and the sponsor pays for bytes it never saw, up to `max_fee`. The red team pins the swapped frame as applying. Fix: the sponsor signs `inner_len`, or a hash of the approvals; the last assertion block of `m1_padding_is_refused_but_a_swapped_mixed_suite_quorum_still_costs_the_sponsor_more` then flips.
- M2, rug relay: Mempool policy, not validity; recorded in the ADR-135 amendment (PR #477).
- M3, builder copy: The block builder copies the whole overlay for every frame that is not a plain transfer, sponsored frames and every v4 form alike, so a block of them is quadratic in touched state. Needs one benchmark before activation.

Node-local admission policy, not validity (security-architect S-5): a node holds at most 64 pending sponsored frames per sponsor, their `max_fee`s summed (checked; an overflow is "cannot cover") within the sponsor's balance, one frame per inner id (the smaller outer frame kept), refuses a `valid_until` more than 86,400 blocks past the admission height, and evicts a sponsored frame before an unsponsored one at an equal rate. A block that breaks any of these is still valid if every frame in it applies.

## Gaps

- SP-3..SP-6 vectors state their inputs; the frames carry real signatures, so `crates/node/tests/sponsored_conformance.rs` builds them from seeded keys and checks the outcome.
- The inner of a sponsored frame may be v5 (a hybrid plain transfer, which the encoder writes for `TxKind::Transfer`) as well as v6-v8; ADR-135's table names v6-v9. Wire v9 is not on this branch.
- TX-4's vectors (`consensus.json`) state the path, not the frame bytes: the reference does not re-implement signatures, so the node builds real v7 (ML-DSA-87) and v8 (2-of-3) frames and checks which call accepts them.
- Typed payloads (channels, DEX, governance) are specified only by the node's code today.
