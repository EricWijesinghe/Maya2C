# 3. State transition — v0.1.0

The accounts-only transfer path. Reference: `crates/spec-ref/src/{stf,root}.rs`.
Node: `StateDB::stage_transaction`, `StateDB::apply_block`,
`state::merkle`.

An account is `(balance: u64, nonce: u64)`. A transfer is applied in this
order, and the first rule that fails is the result:

- **STF-1** The transaction's nonce equals the sender's current nonce; otherwise `InvalidNonce`. (The replay and double-spend guard.)
- **STF-2** The sum of the outputs, each 256-bit (ADR-046), fits in 256 bits at every step; otherwise `BalanceOverflow`.
- **STF-3** The sender's balance is at least that sum; otherwise `InsufficientBalance`.
- **STF-4** The sender is debited and its nonce advanced by one; a nonce at `u64::MAX` cannot advance and is `BalanceOverflow`.
- **STF-5** Each recipient, in output order, is credited; a balance is 256 bits (ADR-046), and a credit past `2^256 − 1` is `BalanceOverflow`.
- **STF-6** The debit is written before any credit is read, so a self-transfer nets to zero and cannot mint. *(positive only: no input is rejected by this rule)*
- **STF-7** An address with no record reads as balance 0, nonce 0; a credit creates the record.
- **STF-8** A block applies all its transactions in order, each seeing the effects of those before it, or it applies none: one failing transaction makes the block invalid and leaves state untouched.

## State root

- **ROOT-1** An account's leaf is `blake3(0x00 ‖ address ‖ balance_u256 ‖ nonce_u64)`: the balance as 32 bytes little-endian (ADR-046), the nonce as 8. *(positive only: defines a value)*
- **ROOT-2** An internal node is `blake3(0x01 ‖ left ‖ right)`. *(positive only: defines a value)*
- **ROOT-3** Leaves are paired left to right; an unpaired last node is promoted unchanged, not duplicated; this repeats until one node remains. With no leaves the root is 32 zero bytes. *(positive only: defines a value)*
- **ROOT-4** Leaves are ordered by ascending address. With no other state layer present, the state root is this accounts root. *(positive only: defines a value)*
- **ROOT-5** Each further layer (channels, notes, trading, governance, …) is folded in, in the order `state::proof::StateLayer` fixes, only once it holds a record, so a chain that never used a layer keeps the root it always had. *(positive only: defines a value)*

## Capped assets (ADR-135 P-1, dark until feature bit 41)

Vectors: `spec/tests/assets.json`, written by hand from these layouts rather than generated by `crates/spec-ref`.

- **AS-1** The forms are `55 ‖ symbol(8) ‖ total_supply(32 LE) ‖ cap(32 LE) ‖ authority(32)` (105 bytes, `RegisterCappedAsset`), `56 ‖ asset(32) ‖ to(32) ‖ amount(32 LE)` (97, `MintAsset`), `57 ‖ asset(32) ‖ amount(32 LE)` (65, `BurnAsset`) and `58 ‖ asset(32)` (33, `RenounceMint`). A truncated form is a decode error.
- **AS-2** An asset record under `d:asset:` is 72 bytes (v1: `creator ‖ total_supply ‖ symbol`, read as capped at its supply with no authority) or 136 bytes led by `0x02` (v2: `0x02 ‖ creator ‖ total_supply ‖ symbol ‖ cap ‖ authority`). Any other length, another leading byte, or a v2 supply above its cap is a decode error. Authority `[0; 32]` means none.
- **AS-3** `RegisterCappedAsset` needs a valid symbol, `0 < cap`, `total_supply <= cap`, `cap <= MAX_ASSET_SUPPLY`, an authority that is the sender or none, and not (zero supply and no authority). The id is `RegisterAsset`'s derivation; the whole supply goes to the sender.
- **AS-4** `MintAsset` needs `amount > 0`, a sender equal to an authority that is not none, and `total_supply + amount` (checked in 256 bits) `<= cap`. It credits `to`.
- **AS-5** `BurnAsset` needs `amount > 0` and the sender's balance of the asset `>= amount`; it lowers the balance and the supply and leaves the cap.
- **AS-6** `RenounceMint` needs a sender equal to an authority that is not none; afterwards the authority is none and the cap equals the supply, so a second renounce and every later mint are refused.
- **AS-7** Below the activation height of feature bit 41 every form is refused, on mempool admission and on apply, by the same check. The compiled height is `u64::MAX`.

## Unique assets (ADR-135 P-2, dark until feature bit 42)

Vectors: `spec/tests/nfts.json`, hand-laid from these layouts. Integers are little-endian unless marked BE.

- **NF-1** The forms are `59 ‖ max_items(8) ‖ metadata_hash(32)` (41 bytes, `CreateCollection`), `60 ‖ collection(32) ‖ metadata_hash(32)` (65, `MintItem`), `61 ‖ collection(32) ‖ index(8) ‖ to(32)` (73, `TransferItem`) and `62 ‖ collection(32) ‖ index(8)` (41, `BurnItem`). A truncated form is a decode error. *(positive and negative vectors: `NF-enc-*`)*
- **NF-2** The collection id is `blake3::derive_key("maya2c nft collection v1", creator ‖ nonce(8))`, 32 bytes. *(positive only: defines a value; vectors `NF-cid-*`)*
- **NF-3** Records under `n:` (one committed layer): `n:c: ‖ collection` holds `0x01 ‖ creator ‖ max_items(8) ‖ minted(8) ‖ metadata_hash` (81 bytes); `n:i: ‖ collection ‖ index(8 BE)` holds `0x01 ‖ owner ‖ metadata_hash` (65 bytes); `n:o: ‖ owner ‖ collection ‖ index(8 BE)` is empty and mirrors the item's owner. *(positive only: record vectors `NF-rec-*`; the refusals are under NF-6)*
- **NF-4** `CreateCollection` needs `1 <= max_items <= 2^32`; the sender is the creator. `MintItem` needs the sender to be the creator and `minted < max_items`; the index is `minted`, which then rises by one. Item and owner rows are written together.
- **NF-5** `TransferItem` needs the sender to own `(collection, index)` and the recipient to differ from the sender; it rewrites the item row and moves the owner row in one write. `BurnItem` needs ownership; it deletes both rows and leaves `minted`, so an index is never reused.
- **NF-6** Only a hash is stored per item and per collection. No URI, no royalty, no sale (ADR-104; ADR-135 cut list).
- **NF-7** Below the activation height of feature bit 42 every form is refused, on mempool admission and on apply, by the same check. The compiled height is `u64::MAX`. A vault account may not send these forms (ADR-030).

## Names (ADR-135 P-3, dark until feature bit 43)

Vectors: `spec/tests/names.json` (hand-laid). Block counts assume one block per second (ADR-135 O-1).

- **NM-1** The forms are `63 ‖ commitment(32)` (33 bytes, `CommitName`), `64 ‖ len(1) ‖ label ‖ salt(32) ‖ periods(1) ‖ target(32)` (70 to 130 bytes, `RegisterName`, label 3 to 63), `65 ‖ len(1) ‖ label ‖ periods(1)` (6 to 66, `RenewName`), and `66 ‖ len(1) ‖ label ‖ op(1) ‖ arg` (`UpdateName`), with op `0x01 SetTarget(address 32)`, `0x03 SetReverse` (no argument) and `0x04 Transfer(new_owner 32)`. Op `0x02` and `0x05` (stealth, ADR-102) are refused at decode in this change. A truncated form is a decode error. *(positive and negative vectors: `NM-enc-*`)*
- **NM-2** A label is 3 to 63 bytes of `a-z`, `0-9` and `-`, with no leading or trailing `-` and no `--`. A label that breaks a rule is refused at decode, so it never reaches execution. *(positive and negative vectors)*
- **NM-3** The commitment is `blake3::derive_key("maya2c name commit v1", label ‖ sender ‖ salt)`. `CommitName` writes `nm:c: ‖ sender ‖ commitment → height ‖ committer` and the expiry-index row `nm:x: ‖ (height + MAX_COMMIT_AGE + 1)(8 BE) ‖ sender ‖ commitment → empty`, is free, and refuses a commitment the same sender already holds unexpired (the age does not reset); an expired, not yet pruned row of the same sender is replaced. Keyed by sender, so another account submitting the same commitment first blocks nothing. *(positive and negative vectors: `NM-cm-*`, `NM-commit-*`)*
- **NM-4** `RegisterName` needs `1 <= periods <= 10`, a commitment by the sender present, an age of `MIN_COMMIT_AGE` (60) to `MAX_COMMIT_AGE` (86,400) blocks inclusive, and a free label (none, or lapsed past the 90-day grace). It burns `NameBaseFee{3|4|5+} × periods` to `FEE_SINK`, sets `expires_at = height + periods × YEAR_BLOCKS` (31,536,000 blocks), and deletes the commitment it consumed and its expiry-index row. A commitment older than `MAX_COMMIT_AGE` is refused and not deleted by that refusal (NM-10 prunes it). *(positive and negative vectors: `NM-reg-*`)*
- **NM-5** `RenewName` may be paid by anyone while the name is live; during grace only the owner may renew; after grace it must be registered again. `expires_at = min(expires_at + periods × YEAR_BLOCKS, height + 10 × YEAR_BLOCKS)`; a renewal that this leaves unchanged is refused rather than charged. *(positive and negative vectors: `NM-renew-*`)*
- **NM-6** `UpdateName` needs an unexpired name. `SetTarget` and `Transfer` need the owner. `SetReverse` needs `target == sender` and may be sent by anyone; it writes `nm:r: ‖ sender`. `Transfer` clears the old owner's reverse record if it names the label; `SetTarget` clears the old target's; a registration over a lapsed name clears both the previous owner's and the previous target's. *(positive and negative vectors: `NM-set-*`, `NM-transfer-*`, `NM-update-*`)*
- **NM-7** `RESERVED_LABELS` is compiled (`maya2c` at index 0). Label `i` is refused while bit `i` of the governed parameter `NameReservedLabels` (tag 15) is set; its default sets every bit, so the hold is in force from activation, and only a passed proposal clearing a bit releases a label (ADR-135 O-3). *(positive and negative vectors: `NM-reserved-*`)*
- **NM-8** Below the activation height of feature bit 43 every name form, and the four name parameters (tags 12 to 15) in a proposal, and a council pause or resume naming breaker module 15 (`Names`; module 14 `Nft` likewise below bit 42), are refused on admission and on apply by the same check. The compiled height is `u64::MAX`.
- **NM-9** The name-fee values are governed 256-bit parameters (tags 12 to 14), per year, all burned. Defaults as built: 1 coin (10^24 base units) for 3 bytes, 0.1 coin (10^23) for 4, and 0.001 coin (10^21), 1/100 of the 4-byte fee, for 5 and longer, so no label length is free. OPEN, not decided: ADR-135's recorded answer (its "Eric's answers" and "economics decisions" tables, PR #477) gives 10^18 / 10^17 / 10^15 base units, and commit 2f38b529 says Eric decided the coin values on 2026-11-12. No recorded decision text shows that. Eric must confirm one set before genesis; the values are governed, so the choice is not consensus-fixed until then. Each may be governed from 0 to 2^252 − 1; a proposal above that is refused. The charge is one checked U256 multiply `fee × periods`, which that ceiling and `periods <= 10` keep inside 256 bits. Pinned by `crates/governance/tests/name_fee_tests.rs` and the `*_burns_exactly_the_length_class_fee_times_periods` tests in `crates/node/tests/names_tests.rs`. *(positive only: defines values; vectors `NM-fee-*`, `NM-reg-periods-10`)*
- **NM-10** At the end of every block at or above bit 43's activation, after every transaction, the node deletes the `nm:x:` rows (and the `nm:c:` rows they name) whose expiry height is at or below the block height, in key order, at most `MAX_COMMIT_PRUNE_PER_BLOCK` (1,024) per block; a row the block already deleted is skipped and the remainder is due first in the next block. *(positive only: a prune is never a refusal; vectors `NM-prune-*`)*
- **NM-11** Breaker module 15 (`Names`) halts commit, register and update; `RenewName` belongs to no module, so a breaker cannot run a name out of its grace period.

## Gaps

- ROOT-5 is pinned by the accounts-only vectors: the node folds every layer it has and must still reproduce the reference's accounts-only root. No vector yet populates a layer.
- The end-of-block passes (sealed swaps, trading, oracle, governance, the names
  commitment prune (NM-10),
  invariant guard) run after the transfers; with no records they are inert,
  which is what the vectors exercise. Their own rules are specified by code.
- The sparse accounts tree (stateless mode, dark) has no vectors.
