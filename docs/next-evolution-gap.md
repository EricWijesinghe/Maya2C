# Next-evolution brief: gap table

Source: [master-prompts/next-evolution.md](master-prompts/next-evolution.md) (Eric, 2026-10-30). It is a brief, not a plan. Before any code it must pass the gate: each item reconciled against `features.toml`, `docs/architecture-vision.md`, `docs/invariants.md` and [ADR-016](adr/ADR-016-launch-scope.md). This document is that reconciliation. It builds nothing.

**Scope.** All 69 brief rows, in the brief's own section order. Nothing here is a status claim beyond what the cited files say. Numbers and superlatives in the brief are targets (Standing Orders 2 and 10).

**Method.** `features.toml` ids and `class/status` read from the file. Paths taken from each entry's `paths` field or from the cited file. Invariant text quoted from `docs/invariants.md`. Wave definitions from [CATALOG.md](ecosystem/CATALOG.md) "Waves". Rung definitions from CATALOG section I: **R0** buildable with what exists now, **R1** needs engineering not yet in hand, **R2** needs a research result. Where an item is a consensus change it is reported against the invariant it touches, and is not designed around (Standing Order 9).

**Columns.** *Exists* gives the `features.toml` id with tier, class and status, then the path. *Collides* quotes the invariant where the item would touch it; "none" means no numbered invariant is touched. *Wave* is W0 (now, non-consensus) to W4 (later), per CATALOG.

**Consensus items are not built here.** Every row that changes consensus, state, wire format or a trusted party needs an ADR under the Standing Orders. "Needs ADR" marks where that applies.

## Ranked: ten items for v3 and later

Assumption: "v3+" means after mainnet v1 and the three-month stability window (CATALOG W1). Ranked by value against risk. Each rank cites its evidence above.

1. **Stateless validation (M6).** Built, tested, dark at `u64::MAX`. Light clients and the scale path without new cryptography. Risk: the sealed, oracle and governance exclusion set, and a witness protocol that does not exist yet.
2. **Kani extended to the apply path and staking (S3, D6).** No consensus change, no new dependency in the core crates. Highest assurance per unit of work. Risk: low. Kani needs bounded models, so it proves less than the brief implies.
3. **Decentralized storage, non-consensus parts first (F5).** `da`, `state-sync` and `archive` exist. Value for light clients and the decentralized-storage item. Risk: low until DA commitments enter blocks, which is consensus.
4. **Parallel execution wired into the node (M7).** Byte-identical to sequential on 100,000 blocks. Value: the throughput item. Risk: medium, because it touches the single apply path (invariant 24). Needs a measured gain before any claim.
5. **Selective disclosure and viewing keys (C6).** Built as research. Gives the regulatory-adaptability item without a default-privacy switch. Risk: low to medium; the anchor is a committed record (25).
6. **Stealth addresses over ML-KEM (C4).** No new primitive beyond ML-KEM, which is verified. Adds the privacy item without changing the default. Risk: medium; it changes transaction verification (31).
7. **Default privacy, after the external circuit audit (C1).** Highest value on the list, and the largest change to what mainnet ships. Risk: highest. Blocked on `CIRCUIT_IS_AUDITED`, and the proof size meets the block cap (33). Eric decision.
8. **Native cross-chain messaging over the Ethereum beacon light client (I2).** Verified in its crate. Trust-minimised messaging rather than a trusted bridge. Risk: medium; each bridge is a trusted party (11) until the light client is wired.
9. **AI-to-AI payments on existing transfers and channels (A5).** Uses `hash-lock-htlc-atomic-swaps` and `l2-flash-settlement`, both built, with no consensus change. Supports the AI-native positioning. Risk: low; agent spend limits are a separate gate (A2).
10. **Post-quantum threshold sealing for the mempool (K5).** The shipped mempool is not post-quantum. Fixing that gap is a security priority for a post-quantum chain, not a new feature. Risk: medium to high; it is cryptographic research.

Not on this list, on purpose: homomorphic encryption (C3), ring signatures (C5), natural-language programming (S4), mobile and browser validators (F1, F2), AI validator assistance as a consensus judge (A7), and adaptive validator selection (K2). Each is R2 or collides with 11, 12 or 13, or needs new cryptography.

## Discrepancies found

- **Older gap doc on master.** `docs/master-prompts/next-evolution-gap.md` (163 lines, 69 rows, bands P2 to P6 instead of waves) was already on master before this document. This document uses the requested path and CATALOG waves. The two overlap. Eric should decide which one stays; nothing was deleted here.
- **ADR-016 is partly superseded.** Its launch table says staking and slashing are "not built" and the fee market is RESEARCH. `features.toml` now lists `staking-and-slashing` as core REAL verified and `eip-1559-base-fee-over-bytes` as core REAL verified. ADR-016 carries an update note on the dag-bft point only.
- **Invariant 20 is retired.** The older gap doc cites invariant 20 for "no floats in consensus rules". Invariant 20 is retired (zkML). The float rule is Standing Order 4 in CLAUDE.md. This document cites the rule by that name.
- **`multi-language-sdks` paths.** The features entry lists `sdk-ffi`, `sdk-wasm` and `sdk-js`. The `sdks/go/` and `sdks/python/` directories exist but are not in the entry's paths.
- **Invariant 4 and ML-DSA-87.** Invariant 4 says `fips204` compiles only `ml-dsa-65`. Invariant 4 as extended by 29 says ML-DSA-87 arrives through the suite registry. Both hold; the wording is easy to misread.
- **Shielded proof size against the block cap.** Architecture-vision gives about 383 KB per joinsplit proof. Invariant 33 sets a provisional 5 MiB block cap. This document computes about 13 proofs per block at the cap. That is arithmetic from two stated figures, not a measurement.
- **Threshold-encrypted mempool is not post-quantum.** Architecture-vision says so in its row. The features entry does not repeat it.
