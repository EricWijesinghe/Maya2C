From a clone of the repository, with Rust installed:

```sh
cargo xtask kit up
```

It builds the binaries, starts four validators with DAG-BFT finality, the API
gateway, the chat relay, the faucet and the explorer, waits until the
validators agree on a chain, and prints every URL and the funded wallet. All
of it listens on loopback with fresh keys. `cargo xtask kit status` says which
endpoints answer; `cargo xtask kit down` stops exactly what `up` started.
More: [testnet kit](https://github.com/EricWijesinghe/Maya2C/blob/master/docs/ecosystem/testnet-kit.md).

**Time from a fresh clone to a running devnet: MISSING.** No recorded run of
`kit up` is in `reports/` yet, and most of it is the first build, which depends
on the machine.

:::note[A private chain, on your machine]
Nothing here is mainnet, and no token is for sale. The public testnet is paused
(since 2026-10-28); [Help run the network](/guides/help-run/) says how to join
when it is back.
:::

## 1. Get Rust and the code

Skip this if `cargo` works and you have a clone. Otherwise choose your
computer: each OS needs different build tools, and Windows uses PowerShell
where Mac and Linux use a Unix shell. Every command has a **Copy** button. The
last step's build is optional for `kit up`, which builds what it needs.

<InstallPicker guide="build" />

The rest of this page follows the same choice.

## 2. Send a transfer on the devnet

`kit up` funds a wallet whose keystore is `target/up/wallet.key`, with the
devnet password `devnet-only-password` (the constant `PASSWORD` in
`xtask/src/devnet.rs`; it protects nothing real). Node 0's RPC is
`127.0.0.1:32000`. The wallet signs only for a chain whose genesis id it is
given (ADR-036), so read that first. From the repository root:

<Tabs syncKey="os">
<TabItem label="Windows" icon="seti:windows">

```powershell
$env:L1_WALLET_PASSWORD = 'devnet-only-password'
$rpc = 'http://127.0.0.1:32000'
$body = '{"jsonrpc":"2.0","id":1,"method":"get_chain_info","params":[]}'
$genesis = (Invoke-RestMethod -Uri $rpc -Method Post -ContentType 'application/json' -Body $body).result.genesis

.\target\debug\l1-wallet.exe --keystore target\up\wallet.key --rpc-url $rpc balance
.\target\debug\l1-wallet.exe --keystore target\up\wallet.key --rpc-url $rpc send `
    --genesis $genesis --amount 500 `
    --to 7777777777777777777777777777777777777777777777777777777777777777
```

</TabItem>
<TabItem label="Mac" icon="apple">

```bash
export L1_WALLET_PASSWORD='devnet-only-password'
RPC=http://127.0.0.1:32000
GENESIS=$(curl -s -X POST -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"get_chain_info","params":[]}' $RPC \
  | sed -n 's/.*"genesis":"\([0-9a-f]*\)".*/\1/p')

target/debug/l1-wallet --keystore target/up/wallet.key --rpc-url $RPC balance
target/debug/l1-wallet --keystore target/up/wallet.key --rpc-url $RPC send \
  --genesis "$GENESIS" --amount 500 \
  --to 7777777777777777777777777777777777777777777777777777777777777777
```

</TabItem>
<TabItem label="Linux" icon="linux">


`send` prints the chain, every output and the fee, and asks before it signs;
`--yes` skips the question in a script. The same transfer from code, in Rust,
TypeScript, Python or Go: the [SDK wizard](/guides/sdk-wizard/).

## Do it by hand: a one-validator chain

The rest of this page builds the same kind of chain without the kit: your own
validator key, your own genesis file, one node. It is the way to see every
piece, and the way a real operator starts.

### A validator key and a wallet

A validator signs its votes with ML-DSA-87 (NIST level 5, ADR-051). A wallet holds a **hybrid** key —
ML-DSA-65 *and* SLH-DSA — and every transaction carries both signatures.

<Tabs syncKey="os">
<TabItem label="Windows" icon="seti:windows">

```powershell
mkdir my-chain; cd my-chain
$env:L1_WALLET_PASSWORD = 'choose-a-password'

maya2c-node --generate-validator-key validator.key   # prints the public key
l1-wallet --keystore wallet.key generate             # prints your address
```

</TabItem>
<TabItem label="Mac" icon="apple">

```bash
mkdir my-chain && cd my-chain
export L1_WALLET_PASSWORD='choose-a-password'

maya2c-node --generate-validator-key validator.key   # prints the public key
l1-wallet --keystore wallet.key generate             # prints your address
```

</TabItem>
<TabItem label="Linux" icon="linux">

```bash
mkdir my-chain && cd my-chain
export L1_WALLET_PASSWORD='choose-a-password'

maya2c-node --generate-validator-key validator.key   # prints the public key
l1-wallet --keystore wallet.key generate             # prints your address
```

</TabItem>
</Tabs>

The keystore is encrypted with that password. On Windows the wallet warns that
it could not restrict the file's permissions; keep the directory private.

### A genesis file

The genesis names the validator set and who holds the starting balance. Put
the validator public key from the step above in `validators`, and your wallet address
in `allocations` and `bonds`:

```json
{
  "chain_id": "maya-local",
  "timestamp": 1790000000,
  "difficulty_bits": 0,
  "pow_limit_bits": 0,
  "allocations": [{ "address": "<YOUR_ADDRESS>", "balance": 10000000 }],
  "bft": {
    "validators": ["<VALIDATOR_PUBLIC_KEY>"],
    "anchor_timeout_ms": 1000,
    "batch_size": 500,
    "fees": {
      "initial_base_fee": 1,
      "min_base_fee": 1,
      "target_block_bytes": 2621440,
      "change_denominator": 8
    },
    "staking": {
      "epoch_blocks": 20,
      "bonds": [{ "operator": "<YOUR_ADDRESS>", "bond": 100000 }]
    }
  }
}
```

Save it as `genesis.json`. The `bft` section is what makes this a DAG-BFT
chain: blocks are ordered and finalised by the validator set, which is the
consensus mode Maya2C launches with.

### Start the node

<Tabs syncKey="os">
<TabItem label="Windows" icon="seti:windows">

```powershell
maya2c-node --genesis genesis.json --data-dir data `
    --rpc-addr 127.0.0.1:8545 --validator-key validator.key
```

</TabItem>
<TabItem label="Mac" icon="apple">

```bash
maya2c-node --genesis genesis.json --data-dir data     --rpc-addr 127.0.0.1:8545 --validator-key validator.key
```

</TabItem>
<TabItem label="Linux" icon="linux">

```bash
maya2c-node --genesis genesis.json --data-dir data     --rpc-addr 127.0.0.1:8545 --validator-key validator.key
```

</TabItem>
</Tabs>

It logs `bft: built block …` about once a second. Leave it running and open
a second terminal in the same directory, and set the password and `PATH` there
too (the same two commands as above).

Keep `--rpc-addr` on `127.0.0.1`. The node's RPC has no authentication; the
public face of a real network is the API gateway, not this port.

The default is `127.0.0.1:8545` (it was `0.0.0.0:8545` before 2026-10-19). A
validator that other operators catch up from (`--catch-up-from`) serves
certificate pages on this port, so it must be given `--rpc-addr 0.0.0.0:8545`
explicitly, and its firewall must allow only the peers it expects. Scripts that
relied on the old default must pass the flag.

### Send a transaction

<Tabs syncKey="os">
<TabItem label="Windows" icon="seti:windows">

```powershell
l1-wallet --keystore wallet.key balance
# balance: 10000000
# nonce:   0

l1-wallet --keystore wallet.key send `
    --to 7777777777777777777777777777777777777777777777777777777777777777 `
    --amount 500 --nonce 0 --genesis <GENESIS_ID>
# status:   accepted into the mempool

l1-wallet --keystore wallet.key balance
# balance: 9972990
# nonce:   1
```

</TabItem>
<TabItem label="Mac" icon="apple">

`<GENESIS_ID>` is the chain's genesis id: ask the node with `get_chain_info`
(as in the devnet step above, on port 8545), or run `send` once without
`--genesis` and the wallet prints it in its refusal. The flag is required since
ADR-036, after the run these outputs come from.

The balance fell by 27,010: 500 sent, and 26,510 in fees. Fees are charged
by size, and a hybrid-signed transaction is about 13 KB — see
[wallet integration](/guides/wallet/) for why.

Read the recipient's balance straight from the node:

<Tabs syncKey="os">
<TabItem label="Windows" icon="seti:windows">

```powershell
$body = '{"jsonrpc":"2.0","id":1,"method":"get_balance","params":["7777777777777777777777777777777777777777777777777777777777777777"]}'
(Invoke-RestMethod -Uri http://127.0.0.1:8545 -Method Post -ContentType 'application/json' -Body $body).result
# address : 7777…
# balance : 500
# nonce   : 0
```

</TabItem>
<TabItem label="Mac" icon="apple">

```bash
  http://127.0.0.1:8545
# {"jsonrpc":"2.0","id":1,"result":{"address":"7777…","balance":500,"nonce":0}}
```

</TabItem>

On Windows the example uses `Invoke-RestMethod` rather than `curl`: in
Windows PowerShell 5.1 a bare `curl` is an alias for `Invoke-WebRequest`,
and quoting JSON for a native program differs between PowerShell versions.

## What was measured

The by-hand outputs are from a real run on 2026-09-29 (Windows 11, dev build,
commit `a6d066f`), not from a mock-up. The `kit up` path at the top has no
recorded run yet, so its time is MISSING. The four-validator version of the same
flow, `cargo xtask bft-devnet`, measured ~0.95 blocks/s, a transfer
visible on all five nodes in 2.1–3.2 s, and every node agreeing on the block at
the common height. Those are one laptop's numbers on localhost, not a
statement about a real network.
